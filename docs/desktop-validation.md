## Limits

The former example conversation/check have been removed from the launch screen. Real tasks have a provider-backed planning/building/review implementation, but no live Nebius calls have been validated in this milestone. Unit loops use deterministic responses, the HTTP adapter is checked against a loopback server, and the real Electron utility worker is exercised with its call budget exhausted so no remote request can occur. These checks do not establish live model compatibility or output quality.

Both new and selected existing source intake are tested. Existing intake is limited to 100 text files and 32 KB total; individual files are at most 16 KB. Hidden paths, common dependency/output folders, symlinks, binary files and detected credentials are excluded. Detection is heuristic, custom ignore rules are not interpreted, and explicit content review remains essential. Output is limited to 12 changed/added files and 48 KB. No deletions are supported. No language whitelist is used.

Automatic code checks remain structural validation plus JSON syntax. Separately approved local commands execute in fresh partial working copies. No dependencies are installed automatically and check outputs are not reused by later checks. Recorded review approval is not a transferable execution grant. Every launch requires a fresh expiring challenge and on-disk workspace/executable checks. Offline acceptance used known fixtures only, not live model-generated code. Draft application is implemented with separate approval, destination baseline checks and retained original backups. Mid-task messaging, concurrent teams and publishing remain deferred. Profile statistics are marked unaggregated rather than presenting fictional counts.

The shell uses Node's built-in SQLite interface; development Node 22 reports it as experimental. It was exercised in the actual Electron runtime as well as unit tests. Reassess stability before release. Short local queries run in the main process; model coordination runs in a separate Electron utility process. Progress is persisted and published as stages finish, not token-by-token streaming.

Windows, Linux, macOS x64, installer behaviour, signing/notarisation, upgrades, cloud execution, live-model-to-local-execution journeys, security penetration testing and comprehensive accessibility evaluation have not been validated. Local process fixtures were tested only on the documented macOS machine. The bundle is unsigned and is not a release installer.

## Security boundary

Application writes are limited to reviewed draft paths. The native directory picker chooses the destination; the renderer cannot supply arbitrary destination paths to the write operation. Selected baseline files and proposed new paths are checked at review and again before writing. Apply reviews include the draft and current review/check evidence, expire after two minutes and are lost on restart. Originals are copied to the app's data directory before destination writes. Unrelated files and Git state are not modified. This is not a multi-file transaction: failures/crashes may leave partial writes, reported through persisted records and a recovery manifest. Recovery is manual, not an automatic rollback. No hostile-filesystem-race or power-loss durability guarantee is made.

Local custom protocol, context isolation, sandboxed renderer, no Node integration, blocked new windows/navigation, denied browser permissions, constrained preload API and sender/payload validation. One model run and one local process may be active at a time; local execution is available only for completed drafts. Keys are held in session memory. Upload and bounded usage require explicit approval. Local execution uses separate program/arguments with no implicit shell, a minimal environment, one-use permission, two-minute review expiry and fresh snapshot copies. These copies are not security sandboxes: approved code can access the user's files and network. Preflight checks are not protection against hostile local filesystem races. Publishing is unavailable.

Local output is saved as untrusted text with a 64 KiB cap; a command has at most 120 seconds. A successful exit is not a correctness verdict. Stop/deadline request process-group termination on macOS/Linux, direct-process termination on Windows; escaped descendants and processes surviving a crash are not guaranteed terminated. Recovery does not replay commands or reuse permission challenges. The storage inventory shows execution artifact counts but has no cleanup control.

Restart marks active runs interrupted without silently retrying them. Local stop discards later worker updates; it does not guarantee remote cancellation. New team runs default to at most three requests for Start working or four with Plan first. Optional early chunk reviews add up to two requests, giving maxima of five/six. Old single-writer runs retain the three-request cap. Requests are fixed to the official HTTPS endpoint, use no storage, reject redirects and have per-request deadlines. Credit/currency balance enforcement and remote cancellation remain limitations.

Current coordination uses a fixed implementation/test/auditor team with optional explicit ownership overrides. Optional early reviews inspect a completed writer's immutable branch while the sibling continues, followed by the final combined audit. A chunk is an entire bounded writer response. Arbitrary task decomposition/team composition, semantic conflict resolution and edits in response to chunk findings remain unimplemented. Review findings are unverified; severity alone does not stop unrelated work. A failed chunk review prevents integration after sibling work settles. This gate uses deterministic provider fixtures, not live multi-agent acceptance. Branches are separate file copies, not security sandboxes; their storage counts are visible but cleanup controls remain pending.

These controls are an initial boundary, not a claim that the future agent runtime is secure. Project access, command approvals, upload policy and untrusted tool-output handling require their own tests when implemented.
