## Objective

Assemble three candidate incident capsules with explicit provenance,
sensitivity, redaction, rights, failure signatures, known-good comparisons,
and expected environment deltas.

## Scope completed

- Selected three Node.js and Express cases covering proxy configuration,
  dependency version, and runtime address resolution.
- Defined a draft capsule for every candidate.
- Defined machine-readable target signatures and known-good non-matches.
- Inventoried every planned artifact by provenance, sensitivity, redaction,
  rights, and handling requirement.
- Limited all evidence to original synthetic artifacts and public technical
  sources.
- Ranked the cases for the next manual reproduction step.

## Tests and validations

- Verified `198.51.100.10` and `198.51.100.11` belong to an address block
  reserved by RFC 5737 for documentation.
- Verified Express documents the effect and security boundary of `trust proxy`.
- Verified the Express 5 migration guide requires named wildcard parameters.
- Verified Node.js documents controllable IPv4-first and IPv6-first result
  ordering.
- Checked changed public documents for invalid whitespace and prohibited
  punctuation.
- Confirmed no generated fixture log, package lockfile, or runtime artifact has
  been represented as already collected.

## Decisions and tradeoffs

- All candidates use the Node.js ecosystem to reduce cross-language setup and
  keep later comparisons focused on the investigation method.
- Synthetic reconstructions are preferred over sanitized real incidents at
  this gate because their data rights and privacy properties are unambiguous.
- The proxy case ranks first because it combines request shape, deployment
  topology, and configuration while producing a clear functional failure.
- The Express upgrade case is likely the easiest deterministic baseline but may
  be too obvious for the final demonstration.
- The address-family case is credible and compact but must prove that the
  sandbox permits deterministic resolver configuration.

## Open questions

- Which exact Node.js and Express versions should be pinned for the fixtures?
- Should the proxy case use an original limiter or a common package?
- Can the target sandbox deterministically control localhost resolution?
- Does one candidate need to come from a real, safely reconstructable incident
  before Phase 0 exits?

## Recommendation

**Approved.** All three candidates can be assembled and tested without
production credentials, customer data, secrets, copied application code, or
unclear rights. Approval should authorize manual fixture construction and
reproduction attempts in Step 0.3. It should not be interpreted as evidence
that any candidate is reproducible or valuable to target engineers.
