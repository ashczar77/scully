# Pearl runtime

Pearl works in a persistent Room chat. A turn may be an ordinary reply, a linked question, or a sequence of project actions and observations. Scully stores the chat and validates every privileged action in the main process. The model does not grant itself project access or command authority.

## Project actions

The user chooses a project folder and approves its scope for the chat. File tools accept relative paths within that folder, reject symlinks and private paths, and limit file sizes. `read_file` can return a bounded line range while reporting the SHA-256 revision of the entire file. Writes require the revision Pearl read. `apply_patch` makes up to 20 exact, nonoverlapping replacements in one file and returns the applied line hunks. An ambiguous match, stale revision, or invalid path leaves the file unchanged. Scully backs up existing content before a successful write. Static browser checks use bounded input, key, and pointer actions. Pointer clicks require a visible, uncovered target.

Commands require a separate approval for the exact executable and arguments shown in the Room. An approval can be used once. On macOS, approved commands run with a temporary restricted environment, a project-local scratch directory, and a system policy that limits file writes to the approved project, blocks reads from common private directories, blocks remote networking, and permits local loopback for application tests. Execution also has time and output limits. Other platforms fail closed. This policy is an interim boundary: it does not provide a full operating-system container, and a command can access project files and local loopback services.

## Progress and completion

The runtime records action results and looks for repeated action-result cycles. It gives Pearl one correction when a cycle repeats, then pauses the turn if it continues. After 32 model responses, it checks for new successful observations every 16 responses. A productive stretch may continue; a stretch without observed progress pauses with its state saved. One uninterrupted stretch also has a 128-response and 15-minute safety limit. The Room offers **Continue** after a pause. Stop also cancels an in-progress browser check and closes its isolated page. New observations show activity, not proof that the user's goal advanced.

After file changes, Pearl must use `complete_work` to report `done`, `partial`, `blocked`, or `unverified`. The backend records which files were written, which commands actually ran, and whether a browser check followed the latest UI edit. It accepts `done` only when a successful command occurred after the latest write and Pearl lists no remaining work. For HTML and style edits, it also requires a clean browser observation after the latest such edit. The browser check observes the initial page and the state after each requested action, so a defect visible only at startup remains in the result. A `partial` or `blocked` result must name what remains. The status and evidence appear with Pearl's final message. A zero command exit and a clean browser observation cannot establish that the requested behavior works across every user journey. An unfinished or untested result must be described honestly.

Chats, questions, approvals, action results, and pause state survive an app restart. An interrupted action with no recorded outcome is marked unknown for inspection instead of being repeated automatically. When a long sequence of tool results pushes the latest user request or Pearl's recent stated approach outside the recent context window, the runtime retains bounded copies for the next model call. The retained approach is labeled as Pearl's recommendation, not user approval. Retained requests, replies, linked answers, and recent messages share an overall character budget. Very long requests may still be shortened, and earlier requirements are not yet compacted by meaning. Operational metrics use bounded outcome categories and durations. They do not contain prompts, source code, command arguments, output, credentials, or absolute paths; external export is disabled.

## Current limits

Context selection uses a character budget, not the selected model's token window, and does not semantically compact a long chat. Patches cover one file per call and are not atomic across multiple files. `browser_check` handles static project pages and bounded actions; it cannot start or inspect a live backend or browse arbitrary sites. Command isolation is available only through the current macOS policy and does not prevent access to every local service or project file. The connected live Room quality gate remains open. See [validation status](pearl-validation.md) for the required journey and observed result.
