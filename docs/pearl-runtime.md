# Pearl runtime

## Remote MCP

Settings can connect one remote HTTPS Streamable HTTP server for the current app session. The optional bearer token stays in memory and is never returned to the Room. Scully rejects local and private network destinations, URL credentials, redirects, oversized tool catalogs, arguments, and responses. Pearl can inspect the bounded tool list, then propose a call. Every `tools/call` pauses for a one-use Room approval that shows the endpoint, tool name, and exact arguments. Replacing or disconnecting the server invalidates pending approvals. The server's descriptions, schemas, and results are untrusted content; a claimed read-only tool still needs approval. Failed remote results do not count as completed project work. OAuth login and multiple concurrent MCP servers are outside this first connection path.

Pearl works in a persistent Room chat. A turn may be an ordinary reply, a linked question, or a sequence of project actions and observations. Scully stores the chat and validates every privileged action in the main process. The model does not grant itself project access or command authority.

## Project actions

The user chooses a project folder and approves its scope for the chat. File tools accept relative paths within that folder, reject symlinks and private paths, and limit file sizes. `read_file` can return a bounded line range while reporting the SHA-256 revision of the entire file. Writes require the revision Pearl read. `apply_patch` makes up to 20 exact, nonoverlapping replacements in one file and returns the applied line hunks. An ambiguous match, stale revision, or invalid path leaves the file unchanged. Scully backs up existing content before a successful write. Browser checks use bounded input, selection, wait, key, and pointer actions. A reviewed `preview_app` command starts a local server with HOST and PORT injected. Its isolated browser keeps cookies and page state across subsequent checks using an opaque preview ID bound to the chat. Source edits invalidate the preview. Completion, Stop, project changes and application exit close it; its maximum lifetime is ten minutes. Pointer clicks require a visible, uncovered target.

`edit_files` proposes two to eight file changes as one reviewed batch. Existing files require the SHA-256 returned by `read_file` in the current chat. The Room shows the complete proposed diff and asks for a one-use decision. Approval revalidates the selected project, paths, revisions, and exact reviewed contents. The backend writes a private recovery journal and originals backup, stages each target beside its destination, then promotes the staged files. A failed promotion rolls back earlier files. On restart, an uncommitted journal is rolled back before the chat resumes; a committed journal is only cleaned up. If an external edit conflicts with recovery, Scully leaves that content untouched and marks the chat for inspection. A batch is not a single filesystem-wide atomic rename: another process may observe intermediate names or race the checks. The batch has a 400,000-character combined before/after limit; ordinary one-file tools remain available.

Each model request has a 90-second backend deadline, including a stalled provider call or response stream. A transport or deadline failure ends the current turn with an actionable error instead of leaving the Room running indefinitely. Continue makes one new model request from the saved user message and completed tool observations, without repeating those actions automatically. It does not restart a partially observed tool action. Without an explicitly configured fallback, connection and timeout failures wait for Continue. With a distinct Nebius fallback enabled, the request switches models if the primary has not begun responding within 25 seconds or fails with a connection, rate-limit, service, or timeout error before its action is accepted. Later steps of the same user turn stay on the fallback, including after approval and restart if the fallback is enabled again. A new user message starts with the selected primary. Authentication failures do not switch models. The selected primary remains configured, and the saved reply and activity identify the model that answered. The Room says when it is retrying from the saved chat. While a turn is running, the Room also reads saved state periodically so a missed update event cannot leave a completed failure or response displayed as working. A timeout does not prove whether the model or network caused the delay.

A single working-plan update may precede a final question, approval or completion action in the same ordered tool batch. No file action may share that batch, and no action may follow its decision boundary. Plan state grants no authority.

Commands require a separate approval for the exact executable and arguments shown in the Room. An approval can be used once. On macOS, approved commands run with a temporary restricted environment, a project-local scratch directory, and a system policy that limits file writes to the approved project, blocks reads from common private directories, blocks remote networking, and permits local loopback for application tests. Execution also has time and output limits. Other platforms fail closed. This policy is an interim boundary: it does not provide a full operating-system container, and a command can access project files and local loopback services.

`start_terminal` uses the same one-use command review and isolation boundary for a process that remains active until stopped or the app exits. At most eight terminals may run per chat and sixteen across the app. The Room shows a bounded output tail, accepts input typed by the user, and offers Stop. Pearl can inspect that output through `read_terminal` and end its own session through `stop_terminal`; only the user can type into it. Typing into an approved shell can start further commands within the project sandbox. The Room connects keystrokes and resize events to a pseudoterminal, so interactive and full-screen terminal programs can run. The latest 128,000 characters of terminal output are retained locally per terminal; earlier output is discarded without stopping the process. Reopening a collapsed terminal may not reconstruct an earlier full-screen display from the retained tail. Updates are coalesced before saving to local storage. A separate local supervisor owns each terminal process group. It stops that group on normal app exit and when its private connection to the app closes unexpectedly. The app also stops the command group if a supervisor exits unexpectedly while the app is running. After an interrupted restart, saved sessions are marked interrupted and are never resumed automatically. A command that deliberately moves itself into a different process group can escape group cleanup; this boundary is not an operating-system container.

Before v2, replace raw-tail-only restoration with a bounded terminal screen checkpoint. Test long full-screen output followed by collapse and reopen, chat switching, and app restart. Keep process lifetime and output storage bounded; screen recovery must not relaunch an interrupted command or bypass its original approval.

## Progress and completion

The runtime records action results and looks for repeated action-result cycles. It gives Pearl one correction when a cycle repeats, then pauses the turn if it continues. After 32 model responses, it checks for new successful observations every 16 responses. A productive stretch may continue; a stretch without observed progress pauses with its state saved. One uninterrupted stretch also has a 128-response and 15-minute safety limit. The Room offers **Continue** after a pause. Stop also cancels an in-progress browser check and closes its isolated page. New observations show activity, not proof that the user's goal advanced.

After file changes, Pearl must use `complete_work` to report `done`, `partial`, `blocked`, or `unverified`. The backend records which files were written, which commands actually ran, and whether a browser check followed the latest UI edit. It accepts `done` only when a successful command occurred after the latest write, the working plan has no unfinished steps, and the completion omits the remaining-work field. Validation errors identify the field or missing observation so Pearl can correct the action. HTML, style and component edits require browser verification. Once a browser check is part of the turn, a passing command cannot override a failed browser result, and any later file edit invalidates earlier browser evidence, including changes to plain JavaScript or server logic. A fresh clean browser observation is required. The browser check observes the initial page and the state after each requested action, so a defect visible only at startup remains in the result. A `partial` or `blocked` result must name what remains. The status and evidence appear with Pearl's final message. A zero command exit and a clean browser observation cannot establish that the requested behavior works across every user journey. An unfinished or untested result must be described honestly.

Chats, questions, approvals, action results, and pause state survive an app restart. An interrupted action with no recorded outcome is marked unknown for inspection instead of being repeated automatically. When a long sequence of tool results pushes the latest user request or Pearl's recent stated approach outside the recent context window, the runtime retains bounded copies for the next model call. The retained approach is labeled as Pearl's recommendation, not user approval. Pending questions are not duplicated when their original tool calls remain in context; trimmed questions are restored from their durable identities. Retained requests, replies, linked answers, and recent messages share an overall character budget. Very long requests may still be shortened, and earlier requirements are not yet compacted by meaning. The working plan is revisioned and retains exact user quotes separately from proposed implementation choices. Rejected updates do not advance its revision or grant approval. The latest source reads stay available while superseded file observations may be compacted. Provider reasoning continuation is replayed unchanged within its active user turn to the same model, including after restart or approval. It is excluded from Room IPC and telemetry. Operational metrics use bounded outcome categories and durations. They do not contain prompts, source code, command arguments, output, credentials, or absolute paths; external export is disabled.

## Current limits

Context selection uses a character budget, not the selected model's token window, and does not semantically compact a long chat. Single-file patches cover one file per call; reviewed batches cover two to eight files with rollback and restart recovery as described above. `browser_check` handles static project pages and approved local live previews with bounded actions. It cannot browse arbitrary sites. Preview navigation and requests stay within the allocated local origin. Command isolation is available only through the current macOS policy and does not prevent access to every local service or project file. Connected Room checks now cover local application implementation and repair, independent browser behavior, restart and provider recovery. Broad dependency-installation and deployment workflows remain unverified. See [validation status](pearl-validation.md) for the exact tested scope and residual limits.

The distinction between focused subagents and visible team teammates is recorded in [agent collaboration direction](agent-collaboration-direction.md). Neither is part of the active Pearl-only workflow.
