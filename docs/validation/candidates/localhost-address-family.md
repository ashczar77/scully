# Candidate 3: Localhost Address-Family Mismatch

**Capsule ID:** `localhost-address-family-v0`

**Status:** Draft for Gate G0.2

**Evidence class:** Synthetic reconstruction based on documented runtime behavior

## Incident narrative

A Node.js worker calls a local sidecar at `http://localhost:3030/health`. The
sidecar listens only on `127.0.0.1`. In the production-like runtime, localhost
resolution returns IPv6 first, so the worker attempts `::1:3030` and receives
`ECONNREFUSED`. A development environment that selects IPv4 first succeeds.

Node.js documents the `verbatim`, `ipv4first`, and `ipv6first` result orders and
their configuration through `dns.setDefaultResultOrder()` or
`--dns-result-order`. See the [Node.js DNS API](https://nodejs.org/api/dns.html).
A public [Node.js issue](https://github.com/nodejs/node/issues/40537) records
the same `localhost`, IPv4-only listener, and `ECONNREFUSED ::1` pattern after
the runtime default changed in Node.js 17.

## Why this qualifies

- The application code and local service can remain identical across runs.
- The trigger combines runtime resolution behavior and bind-address config.
- All network activity remains inside the fixture environment.
- The error code, address, port, and health response are machine-readable.
- The resolver order can be controlled so Step 0.3 does not depend on the host.

## Draft capsule

### Declared environment

| Field | Incident value | Known-good value |
|---|---|---|
| Runtime | Node.js 24 LTS candidate image, pinned during Step 0.3 | Same |
| Sidecar bind address | `127.0.0.1` | Same |
| Sidecar port | `3030` | Same |
| Worker URL | `http://localhost:3030/health` | Same |
| DNS result order | `ipv6first` | `ipv4first` |
| Host mapping | Controlled entries for `127.0.0.1` and `::1` | Same |

The explicit result-order setting provides deterministic reproduction. Runtime
version metadata remains in the capsule because the public incident pattern
originated in a default-order change, but the evaluator does not rely on an
uncontrolled host default.

### Synthetic input sequence

1. Start the local health sidecar on `127.0.0.1:3030`.
2. Confirm direct IPv4 health access returns HTTP 200 and `ok`.
3. Start the worker with the declared DNS result order.
4. Request the health endpoint through `localhost`.
5. Capture resolution order, connection result, process exit, and sidecar log.

### Target failure signature

Signature ID: `localhost-address-family-v1`

Required matchers:

| Matcher | Expected value |
|---|---|
| Worker outcome | Nonzero exit after the health attempt |
| Error code | `ECONNREFUSED` |
| Error address | `::1` |
| Error port | `3030` |
| Sidecar request count | `0` |

Informational evidence:

- ordered `dns.lookup()` results;
- active default result order;
- sidecar bind address;
- normalized connection error stack.

### Known-good non-match

With `ipv4first`, the worker must connect to `127.0.0.1:3030`, receive HTTP 200
with body `ok`, exit successfully, and produce one sidecar request record. The
target connection-refused signature must not match.

### Expected environment delta

The smallest expected delta is DNS result order. A secondary corrective delta
could bind the sidecar to both address families or use an explicit IPv4 URL,
but those comparisons are outside the required initial reproduction.
