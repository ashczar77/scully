# Candidate 2: Express Wildcard Upgrade Failure

**Capsule ID:** `express-wildcard-upgrade-v0`

**Status:** Draft for Gate G0.2

**Evidence class:** Synthetic reconstruction based on a documented breaking change

## Incident narrative

An Express service starts under version 4 but exits during startup after the
deployed dependency resolves to Express 5. The service registers an unnamed
wildcard fallback route. Express 5 requires wildcards to have names, such as
`/*splat`, and rejects the older pattern.

The [Express 5 migration guide](https://expressjs.com/en/guide/migrating-5/)
documents the named-wildcard requirement. A public
[Express issue](https://github.com/expressjs/express/issues/6606) records the
corresponding missing-parameter error for `*` and `/*` patterns. The capsule
will use original fixture code rather than copying the issue example.

## Why this qualifies

- The relevant difference is a deployed dependency version.
- The failure occurs before the service can accept traffic.
- The source, package metadata, and stack trace can be fully synthetic.
- The error has stable type and message tokens after paths are normalized.
- The same source provides a direct known-good version comparison.

### Synthetic input sequence

1. Install dependencies from the declared lockfile.
2. Start the fixture service.
3. Capture process exit, normalized standard error, and port readiness.
4. If startup succeeds, request `/unmatched-path` and capture its response.

No user or customer input is required. The route and request path are created
for the fixture.

### Target failure signature

Signature ID: `express-wildcard-upgrade-v1`

Required matchers:

| Matcher | Expected value |
|---|---|
| Process outcome | Nonzero exit before readiness |
| Error type | `TypeError` or normalized compatible subclass |
| Required message tokens | `Missing parameter name` |
| Required stack module | `path-to-regexp` |
| Readiness probe | No successful listener response |

Unstable absolute paths, line numbers, and documentation URLs in error text are
excluded from matching.

### Known-good non-match

With the same source and the pinned Express 4 lockfile, the process must remain
running, the readiness probe must pass, and `/unmatched-path` must return the
fixture fallback response. The target startup signature must not match.

An additional corrective comparison may replace the route with a named Express
5 wildcard. That comparison is useful evidence but is not required for the
initial reproduction contract.

### Expected environment delta

The expected incident delta is the resolved Express major version and its
transitive router matcher. Application source remains unchanged between the
incident and known-good dependency environments.
