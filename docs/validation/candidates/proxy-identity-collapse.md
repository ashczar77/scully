# Candidate 1: Proxy Identity Collapse

**Capsule ID:** `proxy-identity-collapse-v0`

**Status:** Draft for Gate G0.2

**Evidence class:** Synthetic reconstruction

## Incident narrative

A small Express API works correctly when called directly in development. In a
production-like environment it runs behind a reverse proxy. Two requests from
different clients are treated as the same client by an IP-keyed rate limiter,
so the second client receives HTTP 429 after the first client makes one request.

The suspected production difference is the trusted-proxy boundary. Express
defaults `trust proxy` to false and then derives the client address from the
socket rather than `X-Forwarded-For`. Express documents that proxy topology and
the trust setting must agree because request address behavior changes behind a
proxy. See [Express behind proxies](https://expressjs.com/en/guide/behind-proxies/)
and the [Express application setting](https://expressjs.com/en/5x/api/application/).

## Why this qualifies

- The application behavior is correct without the proxy and fails behind it.
- The trigger combines environment configuration and request metadata.
- The proxy, clients, and limiter can be simulated locally.
- The failure is observable through HTTP responses and structured logs.
- No real client address, traffic, or production configuration is needed.

## Draft capsule

### Declared environment

| Field | Incident value | Known-good value |
|---|---|---|
| Runtime | Node.js 24 LTS candidate image, pinned during Step 0.3 | Same |
| Framework | Express 5, exact version pinned during Step 0.3 | Same |
| Proxy topology | One controlled local reverse-proxy hop | Same |
| `trust proxy` | `false` | Trusted loopback proxy only |
| Limiter | Project-created in-memory limiter, one request per identity | Same |

### Synthetic input sequence

1. Reset the in-memory limiter.
2. Send request A through the proxy with client address `198.51.100.10`.
3. Send request B through the proxy with client address `198.51.100.11`.
4. Record response status, normalized `req.ip`, and limiter-key digest for both
   requests.

The proxy fixture, not the client request, sets the forwarded-address header.
This preserves a credible trusted-hop boundary.

### Target failure signature

Signature ID: `proxy-identity-collapse-v1`

Required matchers:

| Matcher | Expected value |
|---|---|
| Response sequence | `200,429` |
| Rejection event | `rate_limit_rejected` |
| Request A normalized identity | Same digest as request B |
| Request B forwarded client | `198.51.100.11` |
| Process exit | `0` after test completion |

Informational evidence:

- socket address for each request;
- `X-Forwarded-For` value as set by the fixture proxy;
- active `trust proxy` setting;
- limiter bucket state after each request.

### Known-good non-match

With only the controlled loopback proxy trusted, requests A and B must resolve
to distinct client identities and return `200,200`. The target signature must
not match.

### Expected environment delta

The smallest expected delta is the Express trusted-proxy configuration. The
incident setting is `false`; the known-good setting trusts only the controlled
local proxy hop. A blanket `true` setting is not accepted because Express warns
that forwarded headers must be overwritten by the last trusted proxy.
