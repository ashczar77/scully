# Candidate 2: Pydantic Settings Migration Failure

**Capsule ID:** `pydantic-settings-migration-v0`

**Status:** Manually reproduced for Gate G0.3

**Evidence class:** Synthetic reconstruction based on a documented migration

## Incident narrative

A Python API service starts successfully with Pydantic 1 but exits during
startup after a deployment resolves Pydantic 2. The service imports
`BaseSettings` from `pydantic`. Pydantic 2 moved that class to the separate
`pydantic-settings` package, so the unchanged application fails during import.

The [Pydantic migration guide](https://pydantic.dev/docs/validation/latest/get-started/migration/)
documents that `BaseSettings` moved to `pydantic-settings`. A public
[Chroma issue](https://github.com/chroma-core/chroma/issues/774) records the
same `PydanticImportError` after dependency resolution selected Pydantic 2.
The capsule uses original fixture code and does not copy application code or
reporter metadata from the issue.

## Why this qualifies

- The application source remains unchanged between known-good and incident
  environments.
- The triggering difference is a resolved runtime dependency version.
- The failure occurs during service startup and has stable error tokens.
- All source, configuration, logs, and package metadata can be synthetic.
- The fixture needs no database, cloud account, or external service.
