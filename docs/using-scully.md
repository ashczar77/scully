# Using Scully

This guide covers the current desktop workflows and their permission boundaries. Start with the [project overview](../README.md) for setup and validation status.

## First look

1. Start from the empty task list and create a task. Review the current automatic lineup by phase, required requests, reserves and model cost preview in the task form. Switching Plan first or Start working updates the preview. The lineup reflects the current dispatcher; it is not yet a task-specific recommendation or approval of additional specialists. Use **Edit team before creating task** to open Team settings; the task draft is retained. Saving the task captures that team's saved state and does not start a run. Each task can use its own project source. Edit a saved task from its room. After a run is prepared, its start mode is locked, and changes to task details require a new run preparation before upload.
2. The team name appears at the top of the right panel. **Manage team** opens Team settings directly. **Choose team members** shows the 16 fixed profiles. Select three to sixteen characters, including Pearl, at least one builder and at least one independent auditor. Then choose the builder and auditor for current automatic runs and, if wanted, one tester. Pearl receives one planning request for Plan first tasks; other selected characters remain available without automatic model requests. Save the roster to update the current team for new tasks; earlier tasks keep their saved roster. The Team settings preview shows current assignments and request exposure for a new Plan first task. **Create team** makes a separate named copy and selects it for new tasks. The library allows 20 available teams. To delete a team, select another team for new tasks first; deleted teams can be restored from Team settings. Fixed character names, roles, portraits and playbooks cannot be edited in this version. Team, Run usage, and App & connection are separate Settings sections with a sliding selection and reduced-motion support. Run usage asks you to choose a task when none is selected. Dispatching more than one builder, auditor or tester, or a separate on-demand specialist, remains a later gate.
3. Select the saved task to review its project source and run controls.
4. Quit and reopen Scully to verify your task and profile remain.
5. Visit Changes, Preview and Settings to see the current capability boundaries.

Drag the divider beside either side panel to change its width. Focus a divider and use the left or right arrow key for smaller steps; press Home to restore that panel's default width. Scully remembers the widths on this device and keeps the central room readable. The team cards change to portrait rows when the right panel is narrow; portrait frames scale with the panel.

New run events record the teammate name, role and portrait shown when the event was created. Changing the fixed-character roster updates the default team for new tasks, while existing tasks and recorded events retain their saved team or labels. Older events created before identity snapshots have no recorded identity and use the selected task profile as a fallback. The migration replaces earlier editable library teams for new tasks but preserves historical task, run and team snapshots.

Run usage, usage alerts and model cost controls appear as short summaries in the task room. Choose a summary to change its per-run settings. The full token and cost accounting is in Settings. A pause or alert during work remains visible in the task room. Deleting a task before model work starts requires confirmation and removes its saved task, prepared run, usage and cost settings. Tasks with saved work retain their run and recovery records until an archive path is available. Local draft, check, recovery and already applied project files remain unchanged.

## Bounded model run

1. In Settings, enter your Nebius key, exact accessible model ID and output-token limit. Saving configuration does not send a request.
2. Create a task. Choose Plan first or Start working.
3. Choose New project or Existing project. For existing sources, select a folder and inspect/select the files to share. This is a bounded partial snapshot, not a complete repository checkout. Custom ignore rules are not interpreted, so inspect content carefully.
4. Prepare the workspace and explicitly approve sharing and credit use. You can return to the source choice before dispatch; preparing another attempt creates a fresh saved snapshot and requires fresh approval. On fixed-cast tasks, Pearl uses the single Plan first request to prepare a plan, then pauses for your review and a separate build approval. Her response may suggest up to three specialists for specific phases, with a reason for each. At the planning pause, remove or add specialists, set each phase and purpose, then approve the selection (including an empty one) before building. The saved selection is bound to that plan and task snapshot. It does not activate a specialist, send another request or increase the run ceiling. Older saved tasks without Pearl keep their saved planner.
5. If the approved lineup includes a planning specialist, choose **Review consultation** to inspect the exact task, purpose and plan sent to that specialist. Scully shows the selected model, output allowance and available model cost estimate. Input size can raise the actual cost; unknown pricing is shown as unknown. The separate checkbox authorizes one additional read-only model request outside the core run ceiling. Advice and questions appear beside the plan for your review. They do not edit the plan, approve building or trigger another teammate. Each planning specialist can be consulted once for that plan; a stopped, failed or interrupted consultation is not retried automatically. Specialists assigned to later phases are not dispatched by this control.
   To pass answered planning advice to the builders, choose **Review builder handoff**. Inspect the exact saved advice and questions, then separately approve **Attach advice**. You can remove it before building. Attached advice reaches the selected builder and tester writer requests after the usual build approval; it is advisory, does not resolve questions for you, and grants no request or permission. Scully shows the added bytes per writer. Extra input tokens and model cost remain unknown until measured. Changed advice, plan or lineup invalidates the handoff.
   After the builder and auditor finish, an approved **verification** specialist can review the completed draft through the same separate review and approval flow. The exact upload includes the task, plan, generated draft content and saved audit notes. It excludes the original source snapshot and is bound to the currently audited draft revision. The specialist's response is advisory and cannot clear findings, change code, run checks or approve release. Building and release phase assignments still need their own dispatch gates.
6. New tasks use the builder, auditor and optional tester assigned in their saved team. With a tester, the two writers run in parallel in separate private folders, with the auditor reviewing the combined result. Without a tester, the builder owns implementation and test files. The default request ceiling is four with a tester, or two without one, for Start working. Plan first adds one required request. Optional early reviews add one request per assigned writer and do not replace the final audit. The exact saved ceiling appears before approval. Older saved runs retain their own limits. Each request has a 90-second deadline and no automatic retry. The configured token limit is not a currency cap; verify credits and billing controls yourself before use.
7. Review messages, checks, findings and before/after file content. Your original project remains untouched. Stopping halts local coordination but does not prove the provider stopped processing an already submitted request.

While a model request is in flight, the room shows the responsible teammate, activity and locally measured wait time. This status arrives during the request, including parallel writer requests. Structured response content appears only after the request finishes; token-by-token streaming is not available. Stop, failure and restart clear the local in-flight indicator, but do not confirm remote cancellation.

## Team coordination

The ownership panel shows each assigned writer's scope, status and proposed files. The assigned builder owns integration; deterministic integration checks refuse overlapping, case-conflicting, parent/child-conflicting or out-of-scope paths. No writer wins by finishing last. Failed/conflicting branches remain separate for inspection; execution and application stay unavailable. Clarify the task and prepare a new attempt rather than silently rerunning it.

Default test ownership uses visible filename/directory conventions when a tester is assigned, not full language-aware repository discovery. Without a tester, the builder owns test paths too. Before a run starts, open **Configure ownership and early reviews** to override exact files or directory subtrees using the assigned writer IDs shown there. Overlapping rules are rejected. Save settings, then approve the updated request allowance. Settings lock once planning or building starts; changed settings clear prior upload consent.

Optional early reviews are off by default. When enabled, the assigned auditor reviews each completed writer branch while another assigned writer can continue. Each review names an immutable branch revision; findings remain unverified. The final combined audit still runs. A failed early review prevents final integration; no automatic retry occurs. A chunk is currently one writer's complete bounded output, not arbitrary subdivisions within a file or a long-running stream of edits.

Each assigned writer can change up to six files; the combined cap remains 12 files and 48 KB. Stale combined audits block execution/application. Reserves do not receive automatic model requests. Elapsed writer/review time, summed writer time and integration time are observations, not a proven speedup over a single agent. Branch folders are retained beside private drafts; retention controls remain pending.

## Specialist reviews

Completed coordinated drafts expose **Audit testing**, **Audit security**, and **Audit maintainability** buttons. These select review focuses for the task's assigned auditor, not additional independently validated models or an outside specialist. Each dispatch requires fresh upload/usage approval and is tied to the exact draft revision. It uses at most two additional requests: one specialist audit and, if findings are raised, one implementation response. A run permits at most three dispatches, separately counted from its build requests. Failed/interrupted dispatches consume a slot; there are no automatic retries.

Findings and responses remain visible in the room. Contested or accepted findings both require review: discussion is not verification. No automatic code changes, experiments or command execution occur. No findings means only that the reviewer reported none. New specialist evidence invalidates a previously prepared apply approval. Corrective drafts and saved sandbox branches require explicit action; automatic experiment selection and configurable disagreement budgets remain pending.

## Team notes and redirection

Each prepared run has a message panel. **Continue current work unchanged** saves a local note without uploading it or changing the active agent instructions. To change the task, choose **Stop local coordination and prepare a revised plan**. This retains the original run but marks it superseded, blocks its execution/application, and prepares a separate attempt with the redirection, prior plan and prior draft shown for review. It always requests a new plan first, with fresh upload approval and a further approval before building. Earlier local notes are not automatically included in prompts.

For a saved question, **Review reply upload** previews the exact task snapshot before a separate, explicit approval. Replies can run alongside planning, building or auditing through a separate worker. There is at most one reply worker and one coordinator, with the coordinator's existing internal request limits unchanged. Replies are also available on prepared, planned and complete runs; new replies are blocked during a running local check. Each attempt uses one provider request with the configured output-token cap, and at most three attempts per run. Failed attempts consume a slot.

During active work, the two-minute one-use approval uploads the frozen snapshot you reviewed, even if progress advances. Changed selected source, task, question, recipient, redirection or provider settings invalidate approval. The recipient profile comes from the task's saved team, so changing the default team does not alter or invalidate that snapshot. For snapshots reviewed while idle, changes to plan or draft also require a new review. Other notes and command output are excluded. Answers from active work are labelled potentially out of date. **Stop reply** leaves coordination running; stopping or redirecting the task stops both local workers. Remote completion remains unconfirmed. Replies cannot change instructions, execute commands or grant permissions, and are not verification evidence. Interrupted replies are marked failed on restart without replay. Live concurrent-provider behavior remains unverified. Changing direction still requires the explicit revised-plan action, not automatic interpretation of a question.

Local checks must be stopped separately before redirection. Remote inference may still finish or consume credits after local coordination stops. Late worker updates cannot reactivate superseded work, and normal worker/execution saves preserve recorded notes. Messages are capped at 20 per run and 2,000 characters each, with at most three chained redirections. There is no new upload, execution, application or publishing permission implied by sending a message.

Saved questions can be addressed to a teammate, or left as a general engineering reply. Selection uses the task's saved teammate role and instructions, visible in the exact upload snapshot. Changing the selection clears UI consent. Reply history retains the approved identity after later default-team edits. All recipients use the same configured model and the same three-attempt budget. This is one role-focused answer, not multi-model consensus, a broadcast, or a new audit. Profile instructions cannot grant execution or publishing permission.

## Suggestions for later

The final auditor can include up to three optional improvements in its existing response, without additional model requests. They appear after the run completes or stops, in a separate panel bound to the reviewed draft revision. **Mark reviewed** persists acknowledgement only: it neither schedules work nor grants permission, changes files, or resolves findings. Required correctness/security issues still belong in findings. Suggestions are unverified model output and may be misclassified. Legacy runs without suggestions remain valid. Collecting suggestions during every teammate's work and converting them into new tasks are not implemented.

## Local operational metrics

Settings includes **Refresh local metrics**. Instrumentation uses a typed, versioned interface with injectable sinks and a no-op default outside the application wiring. The current sink is an in-memory ring capped at 1,000 events. Events older than 24 hours are removed on reads/writes; exit clears the entire window. No telemetry files, external SDK or exporter are enabled.

Each event contains only schema version, a fixed operation label, returned/threw outcome, rounded duration in milliseconds and a main-process timestamp. Unknown fields are discarded and unknown labels or invalid measurements rejected. No identifiers, prompts, source, arguments, output, paths, credentials or free-text errors are recorded. Sink exceptions and rejected promises do not change operation outcomes or trigger retries. Adapters must remain nonblocking; synchronous adapter work still executes on the calling thread.

Instrumented actions include task creation, source selection, run preparation/start/stop, coordination/session configuration, audit dispatch, finding decisions, correction preparation, command decisions, execution review/start/stop, apply review/write/inspection and storage inspection. These measure backend invocation time, including dialogs where present, not background task or process completion. `model.request` measures a complete provider call in the worker. Counts and means cover only the retained window. A returned action may still contain a failed business outcome; it is not a successful-test or correctness metric. Token usage, cost, detailed failure categories, process/run completion metrics and external monitoring remain future instrumentation work.

## Local artifact inventory

In Settings, select **Refresh storage inventory** to see counts and logical file sizes for draft branches, local check copies and application backups. The scan does not read file content or return paths. It stops after a bounded number of entries per category and labels incomplete or unsafe results as partial or unavailable. Logical sizes are not measured disk usage. The view also counts execution copy names that match saved runs and those that are legacy or unassigned. It checks at most 2,000 saved runs and 2,000 copy names; incomplete results are labelled. A name match is only a clue, not proof of contents or permission to remove a copy. This view cannot delete anything; keep application backups until you have inspected any partial application and no longer need manual recovery.

## Cloud sandbox checks

The desktop can review and submit a bounded Nebius Sandbox check for a completed run. Enter a project ID and API key, search the tagged public sandbox image catalog, and choose an image by name. Scully inspects the selected image and fills in the proposed executable path when it verifies a matching file and execute permission. If inspection cannot verify a match, enter an absolute path for review, marked as unverified. This check does not prove that runtime dependencies work. The app binds the chosen immutable image UUID to the exact command and snapshot files before a separate, one-use approval. It uploads at most 12 files and runs with no guest networking or shell. Execution is disposable by default; saving the environment is an explicit choice included in the review. It saves the operation ID and checks status up to 12 times after a confirmed submission while the panel stays open. Manual status refresh remains available. The key remains in memory, so re-enter it after a restart to refresh an existing operation. No automatic command retry or cancellation occurs. If submission times out, its outcome is unknown and you should inspect Nebius operation history before trying again. This flow has offline fixture coverage only. It has not been tested against a live Nebius account, and the app cannot verify billing or overage settings.

Choose **Save this environment for another experiment** before reviewing a check to retain its filesystem. When Nebius returns a result image, a saved-environment card becomes available for this run and code revision. A follow-up check verifies access to that image, uploads the current reviewed files over their matching paths, and inherits other saved files. Every branch has its own approval and result; the starting image is unchanged. Parent links and returned image IDs survive restart, and all branches share the five-check limit. A saved image can accompany a nonzero process exit, which remains visibly failed. An absent result image creates no new continuation point.

After two completed checks use the same project, draft revision, and starting image, **Compare sandbox checks** shows their service status, process exit, and recorded output side by side. Choose which two checks to inspect when more are available. It compares recorded stdout, stderr, and process exits only when the exact executable, arguments, working directory, timeout, uploaded file hashes, successful service result, and process exits are present on both sides. Otherwise it identifies the differing inputs or missing outcome instead of calling the results like-for-like. Long output is previewed; the individual check retains the captured text. Matching captured output and a zero exit do not prove correctness. Checks from different starting images are not grouped, even when they share a parent checkpoint.

Saving retains files and installed tools, not running processes. Nebius documents 180-day checkpoint retention, after which untagged and unreferenced images may be deleted; tagged or referenced retention and deletion requirements need provider confirmation. Scully has no remote deletion control yet. See [checkpoint semantics](https://docs.tokenfactory.nebius.com/sandboxes/concepts/images-checkpoints-and-branches) and [retention guidance](https://docs.tokenfactory.nebius.com/sandboxes/operate/limits-retention-and-usage).

Operation completion is separate from process exit. Failed or uncertain submissions do not imply that no remote work happened. Returned image IDs are separate from operation IDs, and raw cost fields are not interpreted as currency. The public picker shows the first 100 tagged matches per prefix. Image inspection checks standard executable directories only. Arbitrary private image discovery, cross-run checkpoint reuse, automatic experiment selection, background status tracking across app restarts, explicit cancellation and retention controls remain future work. Cloud execution requires a user-approved transfer and is unavailable without configured credentials.

### Cost visibility

The run's USD warning budget covers model requests only. The cost panel shows the number of Nebius Sandbox check attempts saved on that run separately, with their dollar cost marked unknown. Nebius says the operation response includes a raw `cost` field but cautions that its units and aggregation need confirmation; use the Token Factory Organisation Usage page for billed service spending. The cloud check approval repeats that its price is unknown and the model budget does not cover it. See [Sandbox usage fields](https://docs.tokenfactory.nebius.com/sandboxes/operate/limits-retention-and-usage) and [Nebius billing and consumption](https://docs.tokenfactory.nebius.com/other-capabilities/billing-new).

Tavily is not connected in this build, so Scully makes no Tavily requests. Tavily uses API credits with request-dependent charges and plan-dependent prices. A future integration must track credits and show its own cost exposure before dispatch rather than add an unsupported dollar figure to model estimates. See [Tavily credits and pricing](https://docs.tavily.com/documentation/api-credits).

## Local execution workflow

For a specialist finding, **Prepare corrective draft** creates a separate attempt without uploading or executing anything. Review its parent draft and approve **Build and audit** separately. The attempt uses at most two requests, one corrective writer and one independent audit. Parent files not replaced by the correction remain in the combined draft, within the existing file/size limits. The original run remains unchanged, and no command, finding decision or apply permission transfers. Proposed rechecks require fresh local permission. One corrective attempt per original run is supported, without recursive correction or automatic retries. A completed audit is not a verified fix. Apply still compares against the original selected source baseline, so an already-applied parent may require a new source snapshot.

When an original focused local check fails its proposed criterion, Scully can carry that exact check into the corrective draft if its test file remains unchanged. After separately approving and running it, the room shows both outcomes. If the corrective result meets the criterion, open **Review original finding** to link that result to an explicit finding decision. A still-failing or incomplete recheck cannot serve as corrective resolution evidence. Nothing marks the finding resolved automatically, and a matched criterion is not proof of complete correctness.

Each specialist finding has a decision review: keep unresolved, accept risk, dismiss, or resolve. A reason is required. Resolving requires one to three linked completed checks for the current finding and draft. These are user decisions, not automated proof that a fix is correct. Nonzero exits may be relevant evidence; the user must interpret the assertion and output. Timeouts, interrupted checks and stale results cannot support resolution. Reopening appends history rather than removing an earlier decision. Changed finding/revision/evidence links make previous decisions stale. New decisions invalidate previously prepared apply approvals; they never grant execution or publishing permission.

Specialist responses can propose up to three focused checks within the run's six-command total. Each links a specific finding and snapshot to expected observations. New proposals include a bounded literal criterion: expected process exit and optionally a short output substring. After an approved local or cloud run, Scully evaluates the recorded result against that criterion and reports matched, not matched, or unavailable. It does not execute another command or resolve the finding. The criterion is proposed by the implementation reviewer, not independently validated, and can be weak or wrong. An output-dependent criterion is unavailable if capture is truncated or its completeness is unknown; a confirmed exit-code mismatch can still be reported. Timed-out, interrupted, stale, or uncertain outcomes are unavailable. Older saved checks without a criterion remain visible without a machine result. Empty proposals are allowed when an executable check is not meaningful. The response uses the existing specialist request allowance, without another model call.

Review and run these through the same local execution controls below. Actual output appears beside the finding, with stale evidence labelled. A zero exit does not resolve the finding. New proposals invalidate previous command approvals and execution reviews; previous results remain in history. Finding changes invalidate linked checks. No test code is added automatically and no check output is uploaded automatically.

1. For a completed draft with proposed checks, select **Review local execution**. Denied commands are unavailable.
2. Inspect the resolved executable, arguments, full working directory, timeout and revision. If the runtime is missing, Scully reports it without installing anything.
3. Check the permission box and select **Approve and run locally**. Previous review approval is insufficient. The runner rechecks files and executable content before starting, without an implicit shell or inherited credentials.
4. Watch output and inspect the recorded exit code. A zero exit code means only that the process exited successfully. Findings are not automatically resolved and output is not automatically uploaded for further model review.
5. Stop if needed. Output is capped at 64 KiB, commands at 120 seconds, and each run at 20 executions. There are no automatic retries. Restart marks unfinished executions interrupted, not passed or resumed.

Each check receives a new partial snapshot, so outputs and installed dependencies from a previous check are not reused. Programs can access local files and the network under your account permissions. The minimal environment reduces accidental credential inheritance but is not isolation. Stop requests termination of the process group on macOS/Linux and the direct process on Windows; detached descendants may survive. Windows shell shims are unsupported; direct executables are required. Runtime discovery uses the desktop app's PATH, which may differ from your terminal.

Drafts, snapshots, execution copies (under `executions/` in application data) and output remain local until manually removed; the storage inventory is read-only and has no cleanup control. New execution copy names contain a fixed hash of the run ID, so copies from the same run can be identified after restart, including copies from denied reviews. Older `check-*` copies have no reliable run owner and are left untouched. A matching name alone does not make deletion safe: a local process could alter the directory, and a stopped check may leave descendants running. Preflight checks detect ordinary stale files and symlinks but do not protect against a malicious local process racing file changes. No source is automatically sent to Tavily or Sandboxes in this milestone.

## Review and apply

1. Review draft content, unresolved findings and actual check results. Local command outputs are not automatically incorporated into the draft.
2. Select **Choose destination and review**. All selected baseline files must still match. Added paths must not exist. For a new project, choose an empty folder or a destination with no conflicting paths.
3. Review the full destination and exact before/after content, then explicitly approve **Apply reviewed files**. Reviews expire after two minutes, cannot be reused, and are invalidated by changed draft or review evidence.
4. Inspect the application record. Only draft files are written; unrelated files are preserved. No deletion, commit or push occurs. Originals and a manifest are retained under `applications/` in the app's local data directory.
5. Select **Inspect recovery state** to compare the saved manifest and originals with the current destination. Missing, changed or unsafe evidence is reported without changing files. Refresh the inspection after any further edits.

Multi-file application is not atomic. If a write fails or the app closes, earlier files may already be written. Inspect the destination and recovery evidence before manually restoring originals; Scully does not automatically roll back over later user changes. Failed/interrupted applications cannot silently retry the same draft. Recovery inspection is a current snapshot, not proof of file history or safe restoration. Automatic merging and backup retention controls remain future work. Avoid concurrent editing during application; path checks do not defeat a malicious local filesystem race.

Only macOS ARM64 is being validated at this milestone. Windows/Linux installation and signed distribution are pending. See [desktop validation](desktop-validation.md) for exact checks and limits.
