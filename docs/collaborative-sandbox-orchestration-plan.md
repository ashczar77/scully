# Collaborative sandbox orchestration plan

Status: **implementation in progress, not accepted as complete**. The repository now contains structured planning, dynamic staffing proposals, per-assignment collaboration and environment selection, and offline regression coverage. A bounded live planning check and an earlier limited live Sandbox adapter check are recorded in [desktop validation](desktop-validation.md). The assignment dependency graph can start multiple teammates and add reviewed specialists, but it does not yet support the full split, combine, reassign, and cancel work-item lifecycle described below. The complete model-driven desktop workflow, mixed-image execution, and full acceptance matrix have not been demonstrated. Do not describe Scully as delivering this plan until those criteria are observed.

Review note: implementation was explicitly authorized after this plan was reviewed. Live checks should remain bounded and use configured access. Validation evidence is recorded in [desktop validation](desktop-validation.md); this plan alone is not evidence that remote behavior works.

Scully is a desktop workspace where a team can plan, build, test, review, and discuss a software project with its user. The selected local project folder is the project's source of truth. When Nebius Sandboxes are configured, an approved build should use independent, branchable sandbox environments so teammates can work at the same time, inspect each other's progress, resolve dependencies, and recover from failures. A local-only option must remain available for projects the user does not want uploaded.

This document records the earlier team implementation and acceptance plan. Team work is outside the active Pearl-only Room. This plan distinguishes intended design from repository evidence. [Historical desktop validation](desktop-validation.md) records checks that actually ran, but passing fixtures or a narrow Sandbox adapter exercise is not proof that a model-led team can complete the workflows in this plan. The current solo scope and gate are in [Pearl validation](pearl-validation.md).

## Product decisions

- The Room is a real team conversation. Teammates ask direct questions, answer one another, and report observed progress. Dialogue is not assembled from preset handoff lines or fixed numbers of exchanges.
- Questions to the user appear in the Room, with a badge on the asking teammate. A question has an explicit pending, answered, or withdrawn state so the badge clears for the right reason. The user can answer naturally without numbering responses or addressing only Pearl.
- Pearl coordinates planning, dependencies, and the team. She does not claim to write code, start building while still planning, or dispatch a team before its proposal is ready for review. She asks no more than two related user questions at once and includes recommendations.
- Pearl and every teammate choose collaborators from the actual task, project evidence, current findings, and available people's capabilities. A saved roster is a set of possible participants, not a fixed one-builder, one-tester lineup. A task may need multiple builders, testers, auditors, or specialists, or no specialist at all. A person outside the selected team is proposed to the user rather than silently added.
- Any teammate can identify a need for another person during planning, building, testing, or review. They can provide evidence and ask Pearl to assess and coordinate the addition. Pearl may consult relevant teammates during planning as often as useful within progress and resource safeguards. No schema or policy imposes an arbitrary single consultation or single specialist per turn.
- Every active or newly dispatched teammate participates in the same communication, checkpoint, visibility, and recovery system. Approved role permissions determine whether a teammate can edit, execute, advise, test, or audit.
- A configured Nebius Sandbox is the default collaborative build environment. Local-only work is an explicit alternative. The selected local folder stays authoritative; sandbox branches are isolated work environments, not replacement projects.
- Each teammate's starting image and tools must suit their assigned work. A shared default image or first tag match cannot stand in for that decision. When no available image can safely support one teammate's work, pause that teammate, present the required local commands and file scope for user approval, and let independent teammates continue.
- The user can see each teammate's sandbox activity, changed files, checks, and checkpoints. Selecting a file opens it in a central preview or editor while the file list remains available.
- A failed step preserves useful work, states what is known, and offers relevant ways forward. It does not invent a cause or leave the task at a dead end. A stalled agent can be paused with **Continue** and **Redirect** actions. Unaffected agents may continue.
- Scully imposes no default lifetime model-request count. User-set limits and usage alerts remain available. Automatic retries are bounded by progress, repetition, permission, and spending guards.
- Model selection lives in Settings. Pearl defaults to Nemotron 3 Super; builders, testers, auditors, and each specialist default to Nemotron 3.5 Lightning. A searchable model modal shows the two recommendations first, then all returned models, with incompatible models disabled and explained. Each member can have an appropriate thinking preset.
- The Room renders supported Markdown as formatted content, preserving paragraphs and lists. It does not flatten newlines or rely on growing lists of regex substitutions to make model text readable. Names, portraits, and send times are separate from message bubbles; teammate bubbles have distinct colors, sufficient spacing, and clickable profiles.

## Remove scripted and brittle interaction rules

This is a repository-wide migration requirement, not a prompt wording change. Before implementing the new runtime, inventory rules in prompts, backend orchestration, shared helpers, UI rendering, tests, and documentation. For each rule, record its purpose and classify it as **remove**, **replace with explicit state or a standard parser**, or **retain as a justified boundary**. Remove superseded paths when the replacement is verified; leaving both active would preserve the old behavior and make failures hard to diagnose.

The earlier rule inventory identified phrase-specific dialogue repair, numbered-answer matching, keyword intent detection, canned handoffs, one-shot file contracts, and partial Markdown rendering. The direct-workspace path used structured question and assignment records, a Markdown parser, and per-assignment environment inspection. Historical records still use the old rendering and lineup helpers. Review any remaining legacy helper at its call site before removal, and do not remove a valid security or protocol parser merely because it uses a regular expression.

Remove text-replacement and regex chains that try to interpret or rewrite the meaning of user or teammate messages. Do not repair a model reply by deleting phrases such as "before I start coding," changing "the user wants" to "you'd like," matching only numbered answers, or inferring a user's intent from a few opening keywords. Those techniques have caused lost formatting, repeated questions, false routing, and misleading claims. A new wording failure must not be handled by adding one more substitution.

Replace those heuristics with durable question and decision records, model reasoning over relevant conversation and artifacts, explicit tool results, and clarification when meaning is uncertain. Keep the original message content intact in the conversation record. Replace canned start, handoff, and failure messages with real event state plus agent-authored conversation where a reply is needed. Use a maintained Markdown parser and safe rendering policy for model text; do not strip Markdown into plain text, flatten structured text, and then try to repair every observed wording pattern. Remove limits that exist only because a writer must return whole files in one response, such as the current small file and output contracts, as the tool loop takes over. Evaluate each remaining resource limit against actual service constraints and runaway protection instead of carrying forward arbitrary counts.

Keep deterministic checks where correctness or security requires them: schema and path validation, role and tool permissions, revision binding, one-use approvals where required, provider compatibility, idempotency, and rolling spending or no-progress guards. These rules constrain actions, not what a teammate may naturally say or how many useful exchanges can occur. The user's preference for no more than two related questions at once is a presentation and pacing rule, not a lifetime conversation cap.

Completion requires tests with previously unseen, unnumbered user replies, questions from different teammates, changed decisions, overlapping work, varied Markdown, and recoverable provider failures. Tests must prove the new state and tool flow works; they should not merely encode another list of phrases to replace. Verify that ordinary message text reaches the Room without semantic cleanup, and that Markdown is parsed and rendered safely instead of displayed raw or removed with regex. Remove or update old tests and user documentation only when their acceptance criteria have intentionally changed, and record the reason.

## Core architecture

### Project source and branch lifecycle

1. Before a build, Scully inspects the selected local checkout or project folder and records a base revision and an upload manifest. The right-hand Files view shows that folder immediately, including before any agent writes a file. Ignored files, secrets, and material outside the approved scope are excluded from upload.
2. With configured Nebius Sandboxes and an approved upload and execution scope, Scully selects a compatible starting image for each assignment and prepares that agent's environment with the approved project snapshot. Different roles may need different images. It records each immutable image UUID, shared source-manifest hash, project identity, observed capability check, and effective permissions.
3. Each approved teammate who needs write access starts from its own compatible, source-equivalent checkpoint on an independent branch. Subsequent saved operations advance only that branch. Read-only teammates can inspect an immutable checkpoint without gaining write authority. A teammate joining mid-task starts from a current, relevant source revision and compatible environment and receives the latest task decisions, not just the original prompt.
4. Each agent can publish an inspectable checkpoint before its assignment is complete. The checkpoint carries parent image, owner, file manifest, diff, checks, and status. Other teammates can inspect it, ask about it, or incorporate it into their own branch under their permissions.
5. An integration workspace combines compatible changes as they become ready. Conflicting edits are reported with exact paths and revisions to the responsible owners. An owner can revise their branch; no branch silently wins by finishing last. The tester and auditor can inspect integrated checkpoints while other approved work continues.
6. Scully synchronizes a reviewed integration to the selected local folder with preflight checks against the recorded base and any intervening user edits. It presents conflicts rather than overwriting user changes. The local Git history remains real Git history; Nebius image branches are execution checkpoints, not Git commits.

Nebius defines a branch as an independent operation from an immutable image. Saved images preserve files and installed dependencies, but not processes, memory, or live services. Scully therefore needs its own durable branch graph, file exchange, and merge logic; the sandbox service does not provide a shared writable checkout or resolve Git conflicts for the team. See [Nebius images, checkpoints, and branches](https://docs.tokenfactory.nebius.com/sandboxes/concepts/images-checkpoints-and-branches) and the [ConTree SDK session model](https://github.com/nebius/contree-sdk#core-concepts).

### Agent runtime and communication

Each teammate has a persistent task thread and a bounded tool loop. A model can request an authorized action, receive its result, inspect the changed workspace, and decide what to do next. The runtime preserves conversation state across calls and can resume from a checkpoint after interruption. A model response is a proposal, never permission to expand its scope.

A durable task event stream connects the Room, agent threads, branch state, and audit history. Messages have an actor, recipient or audience, task and branch revision, timestamp, message type, and references to any relevant file, diff, check, question, or checkpoint. Their natural-language content remains flexible. The backend validates routing and permissions; it does not prescribe the words or count of teammate exchanges. Agents can message peers directly, while Pearl sees enough of the exchange to manage dependencies without becoming a bottleneck. The user sees meaningful discussion in the Room and can open detailed activity when needed.

Task decisions and interface contracts are versioned shared state. Each agent receives the relevant decisions and a precise checkpoint reference, while keeping its own working context. Switching models does not transfer a model's hidden state; Scully must explicitly provide the teammate's thread, current decisions, and referenced artifacts. If a decision changes, dependent work is marked stale and the affected agents are notified.

Questions are first-class records with an owner, recipient, status, and resolution linked to a user or teammate message. A teammate should ask another teammate when that person can answer from implementation evidence. Product choices, changed scope, permissions, additional spending, publication, and acceptance of risk go to the user. User replies can be conversational; resolution should be based on meaning and explicit linkage, with clarification when an answer remains ambiguous. The badge clears only when the question is resolved or withdrawn.

For example, Maya can publish a storage interface checkpoint and ask Jun to check a behavior. Jun can inspect it, run or adapt tests, and ask Maya about an ambiguity while she continues implementing. If either needs an authentication product decision, that question goes to the user. This is concurrent work with communication, not two isolated requests that happen to start together.

### Planning, suitability, and team formation

Pearl's first job is to understand the user's outcome and the actual project. She should inspect the approved repository snapshot, existing architecture, language and framework, tests, UI, stated product constraints, and relevant prior decisions. She distinguishes observations from assumptions and asks the user about choices that materially affect the outcome, security or data boundaries, or difficult-to-reverse architecture. A brand-new project with no source must be analyzed from its requirements rather than treated as if a repository exists. A request to plan or answer a question does not authorize building.

The task's saved roster is a pool of available people, not an assignment or a guarantee that every needed capability is present. A candidate record should expose the person's actual specialty, working instructions, available tools, model capability, role restrictions, and current workload. Pearl may use focused consultations during planning with relevant available people. An agent may also explain why a consultation is unnecessary. The system must not limit consultation to one slot in a response schema or require exactly one specialist merely to create a sense of teamwork. Its rolling resource and no-progress guards still apply.

Pearl proposes an assignment **set**, not fixed builder/tester/auditor fields. Each proposed assignment includes the person, purpose, concrete deliverable or question, evidence of fit tied to the task or project, dependencies, intended workspace and tools, checkpoint to inspect, permission scope, expected coordination partners, and any cost or user decision. The model reasons about suitability. The backend validates that cited artifacts and candidates exist, roles and tools are compatible, scopes are permitted, and review requirements are met. Validation of a reference is not proof that the model's judgment is correct. Show the user reasons for important assignments so they can challenge or change them.

If selected people lack a needed capability, Pearl says so and proposes an appropriate person from the available catalog for user review. If the catalog lacks that capability, she exposes the limitation and asks whether to proceed with a narrower scope, a different team, or an external/manual contribution. She must not choose Maya, Jun, Ellis, or the first matching roster member as a silent fallback. If a model returns an invalid proposal, return a validation result to Pearl for revision. Repeated invalid proposals lead to an inspectable pause with a way to edit or redirect the team proposal, not a fabricated fit claim.

Planning consultations may occur before a final team proposal. They are advice, not an undisclosed approval to start building or to add someone permanently to the team. Pearl must keep unresolved user questions in durable state and may explain a tentative recommendation while waiting, but the Room cannot present a final plan or approved build team until those questions are resolved or explicitly withdrawn. A question typed in a Room message must be represented by a question record; a missing Markdown section cannot mean that no question exists. If the user gives a free-form answer, the model evaluates it against the open decisions, records the supported resolution, and asks one narrower follow-up when ambiguity matters.

### Dynamic work division and communication

Model work as a changing dependency graph rather than a fixed build, test, review sequence. Each work item carries an objective, owner or candidate owners, required input revisions, dependencies, expected artifact or evidence, permissions, status, and completion or review conditions. Pearl may create, split, combine, reassign, or cancel work items as evidence changes, without erasing the history of earlier decisions. Parallelism is chosen because work can genuinely proceed independently, not because the UI expects a fixed number of teammates.

For a large project, two builders can own separate components or interfaces, publish intermediate checkpoints, and agree on a shared contract. Two testers can cover distinct behavior, such as unit-level logic and end-to-end keyboard accessibility, and can inspect changing integrated revisions. Auditors can review defined scopes or independent portions of a large change. Overlapping edits or tests must have named owners and integration rules. If a dependency blocks one work item, other independent work continues. The coordinator can revise the graph when one agent uncovers an unexpected integration or product issue.

Every teammate, including builders, testers, auditors, and specialists added later, has the same ability to report an observation, ask a targeted question, request a peer's review, or recommend help. A request for another teammate is a first-class action containing the problem, supporting file/check/revision references, capability needed, suggested person if known, urgency, and what the requester tried. Pearl can consult others, accept and propose dispatch, ask for more evidence, or explain why the existing team can handle it. A reviewer who finds weak code can request a security, UI, accessibility, performance, or other specialist based on the defect itself. A specialist can also identify a need for another role. The backend validates scope and permissions; it does not classify the defect or select the person with keyword rules.

Direct peer conversation should be possible when the recipient can resolve a technical question. Pearl receives the dependency and outcome in shared state and joins when coordination or a user decision is needed. Agents should refer to actual checkpoints, tool results, and decisions, not pretend to have seen unpublished branch work. Messages and model requests need bounded context selection and summaries with source references so a long project remains usable without losing decisions. A peer response can change an assignment, a plan, or a branch, but only through an explicit recorded action. The Room shows meaningful exchanges; repetitive status chatter and scripted acknowledgments are not required.

Pearl should speak as a coordinator: acknowledge what changed, state the consequence, name the person taking the next action when known, and ask a direct question when a decision is needed. She must not claim to have written code, run tests, resolved an open choice, or secured a teammate who has not accepted an assignment. Conversational quality is evaluated from actual transcripts and user tasks, not enforced with phrase replacement. The system should not attempt to impersonate a human or hide uncertainty. A short visual typing transition may accompany a real pending response, but no synthetic back-and-forth is generated to fill time.

### Per-agent execution environments and mixed modes

An agent's required environment is derived from its proposed work and project evidence: language and runtime, package manager, tools, test commands, operating-system needs, architecture, network requirements, and permitted files. The image catalog is only a candidate list. Inspect image metadata and, when necessary and authorized, perform a minimal capability probe before selecting one. Pearl or the assigned agent explains the choice. A tag containing `node` is not evidence that a Java test suite or Rust build can run there. The user may change the proposed image, which triggers compatibility and scope revalidation.

The approved source snapshot must be transferred into each compatible agent environment. Different agents may use different base images while sharing the same logical source revision. Track the base image UUID, source manifest hash, agent branch head, installed tooling, and operation lineage separately. Cross-image collaboration exchanges reviewed files, diffs, test evidence, and explicit checkpoint references; it cannot assume that an image produced under one base can be used directly as another base. Integration is a revision-controlled file operation, not a shared writable Sandbox.

If no listed image can run an agent's required operation, Scully pauses **only that agent** with the observed incompatibility and preserves its last good checkpoint. It presents a concrete local-execution proposal: commands and arguments, working directory, file read/write scope, relevant environment and network access, expected output, and the fact that local processes run under the user's account. The user can approve those exact actions, choose another image or approach, redirect the agent, or leave it paused. Approval is bound to that actor, task, command and file scope, and current revision; it cannot silently become blanket local access. Other agents may keep working in Sandboxes. A local agent publishes artifacts into the same revision and review system so mixed-mode integration is explicit and safe. If no safe path exists, explain the blocker and offer reassignment or scope change instead of failing the whole task.

### Durable records and concurrency contract

The backend should persist a task record, approved scope and base manifest; one thread and inbox per teammate; messages and question resolutions; branch heads and their immutable parent image UUIDs; sandbox operation IDs and outcomes; integration revisions; review findings; and local synchronization results. Every message, check, approval, and merge decision references the revision it concerns. Persist an event before presenting it as complete in the UI. A restart reconstructs the Room and each branch from these records rather than re-running model actions.

Only one mutating operation may advance a particular branch head at a time. Different branches can advance concurrently within the account-effective Nebius limits and the user's approved resource policy. An agent may inspect another branch's published checkpoint, but never mutate that checkpoint or assume unpublished work is visible. Importing another agent's work creates a new revision on the recipient or integration branch. Keep the parent and imported revision IDs so stale reads and conflicting updates can be detected.

Each tool action has a recorded actor, scope, input revision, operation ID or idempotency key where available, and terminal outcome. A timed-out submission is **uncertain**, not automatically failed; reconcile its operation status before retrying. A saved result image is usable only after it is returned and inspectable, including when the command itself exited nonzero. A missing result image leaves the previous known-good checkpoint as the continuation point. These conditions follow Nebius's [result-image guidance](https://docs.tokenfactory.nebius.com/sandboxes/concepts/images-checkpoints-and-branches#interpret-the-result-image).

Sandbox visibility means immediate start, status, and completion events, followed by file and diff inspection when a result image becomes available. It does not promise per-keystroke visibility into an operation or a live shared filesystem. The UI must label the local folder, each agent branch, and the integration workspace so users know where a displayed file actually exists.

### Dispatch applies to the whole team

The dispatcher can bring in any approved builder, tester, auditor, or specialist when their skills are relevant, including a second or third person in a role. Pearl may recommend a teammate during planning or later work, and any active teammate may request one through Pearl. The proposal records the observed need, candidate and evidence of fit, task and dependency, intended scope, context to share, environment, permissions, and spending impact. People outside the user-selected team and expansions of approved authority require user review. A reviewed dispatch joins current work from an appropriate source revision and compatible environment with the latest decisions and relevant conversations. Declining the proposal keeps the existing team intact and lets Pearl revise the work assignment.

All teammates can communicate and expose progress. Edit and execution rights remain role- and task-specific. A specialist can advise, investigate, or review without an automatic right to alter production files. An auditor remains independent of changes it reviews. A teammate may request an additional capability, but the backend must enforce the resulting decision; a message or prompt cannot grant it. A proposed assignment is not considered accepted merely because a model named a person; its roster, permission, environment, and user-review requirements must be satisfied before that person acts.

## Visibility in the desktop app

- **Room:** user and teammate messages, direct questions, decisions, substantive work milestones, and recoverable pauses. A short typing transition may improve readability, but it reflects a real pending event; Scully does not insert artificial dialogue or a minimum delay.
- **Activity:** each active teammate's current model request or tool operation, elapsed time, sandbox operation status, checks, checkpoints, and failures. Start and finish events appear even if an operation produces no files. The display distinguishes observed activity from a claim that work succeeded.
- **Files:** the selected local folder, integration workspace, and each teammate's branch are clearly identified. The file list updates when a sandbox result becomes inspectable. A file opens centrally with source, revision, and diff context; it does not imply that an unmerged branch file is already on the user's disk.
- **Changes:** actual Git branches, commits, and working-tree changes from the selected local repository. When no repository is configured, the page offers setup or help from Pearl. Sandbox checkpoint lineage is available as task activity rather than being mislabeled Git history.
- **Settings:** per-member models and thinking presets, advanced output controls, usage and spending settings, and the searchable model catalog. Output allowance is chosen for the model and task by default; an advanced override remains possible.

Show staffing proposals as assignments with reasons and dependencies, rather than a decorative fixed list of three people. Show when a teammate requested help, Pearl's assessment, whether user review is needed, who joined, and what context the new teammate received. For parallel work, distinguish each person's work item, branch or local workspace, active operation, and last verified checkpoint. A dependency indicator must not label a still-working agent as failed. The user can inspect a full event history without flooding the default Room view with low-level tool output.

The Room composer must remain focusable and editable in planning, running, paused, and failed states unless an explicit, visible permission boundary blocks sending. The question owner and pending decision must be clear even when the user replies without numbers or mentions. Lists and paragraphs must have proper spacing. Saving a planning temperature should show a padded, styled, temporary confirmation rather than a permanent "Saved" label beside the button. The Sandbox connection uses the same confirmation design as the model connection; configuration, access checked, and unavailable are separate states. Model selection uses a searchable modal with pinned recommendations and the rest of the returned compatible catalog. The Sandbox image list is searchable and collapsible, with compatibility reasons and the selected agent's needs visible rather than an unstyled list of every tag. Buttons and controls follow the application's spacing, focus, and keyboard styles. Failure diagnostics must be available in the app and in privacy-safe local logs; an empty terminal must not be the only explanation for a stopped task. The existing Chromium disk-cache messages require separate diagnosis and must not be presented as the cause of a model or build failure without evidence.

## Failure handling and recovery

An operation failure is not automatically a task failure. Scully records what was attempted, what completed, what is uncertain, and the latest usable revision. It pauses only the affected dependency unless other work cannot safely continue. The Room offers actions grounded in that evidence.

| Observed condition                                                      | Default response                                                                                             | User path when needed                                                      |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| Response truncated at the model output allowance                        | Preserve prior checkpoint; retry or continue with an appropriate allowance and smaller step when safe        | Continue or redirect the agent                                             |
| Response contains no file change and no blocking question               | Ask the agent to inspect its tool results and state its next step; do not infer missing requirements         | Continue, redirect, or reassign after repeated lack of progress            |
| Recoverable provider or transport error                                 | Retry with bounded backoff only when duplicate work cannot cause harm                                        | Continue when retry allowance or service availability is exhausted         |
| Sandbox submission outcome unknown                                      | Inspect operation history and status before resubmitting; never assume it failed                             | Inspect status, then choose a safe continuation                            |
| Command or test fails                                                   | Preserve output and checkpoint; let the responsible agent investigate and communicate with teammates         | Redirect or accept a documented limitation where permitted                 |
| Branches conflict or a dependency changes                               | Keep both branches and identify exact files, owners, and revisions                                           | Ask owners to reconcile, choose a direction, or revise scope               |
| Agent repeats an unproductive action or spends rapidly without progress | Pause that agent and retain all inspectable work                                                             | Continue or Redirect with a concise explanation                            |
| Selected team lacks the capability an agent's finding requires          | Pearl evaluates the evidence and proposes a suitable person or narrower scope; no silent roster substitution | Review a teammate addition, redirect, or change the scope                  |
| No compatible Sandbox image exists for one agent                        | Pause only that agent, preserve its branch, and prepare an exact local-execution proposal                    | Approve scoped local work, choose another image, redirect, or leave paused |
| A teammate asks for help or reports a defect during another's work      | Preserve the finding and route it to Pearl and the relevant peer with revision evidence                      | Review any required team or permission expansion                           |
| One agent's provider or Sandbox operation fails while peers can work    | Preserve that agent's checkpoint and continue independent assignments                                        | Continue, Redirect, reassign, or change environment                        |
| App closes or worker stops                                              | Recover durable task, branch, and operation records; reconcile any uncertain remote operation                | Resume from the last verified checkpoint                                   |

Automatic recovery uses error type, idempotency, observed progress, and rolling resource usage. It does not impose a small default lifetime request cap or allow an agent to loop indefinitely. Unknown token or sandbox cost is displayed as unknown, never zero. A failed check is not a verified fix, and a successful process exit is not proof of task correctness.

Track task status separately from teammate status. A task can be running while one teammate is waiting for a peer, awaiting the user, or paused for lack of progress. A teammate's recoverable failure does not mark the whole task failed. The task pauses only when a required dependency cannot proceed safely. **Continue** resumes from a recorded checkpoint after showing the cause and likely cost; **Redirect** records new guidance and sends it to the affected teammate without erasing branch history. Reassignment starts a new authorized teammate from a specified checkpoint. None of these actions replays an uncertain external operation blindly.

Diagnostics must separate provider rejection, output truncation, invalid tool arguments, permission denial, incompatible or missing environment, sandbox service failure, command exit, integration conflict, and local synchronization failure. Show the responsible teammate, stage, last verified revision, observed error code, and available actions. A model output with no file changes is not necessarily a failure; it may be a question, inspection result, or decision. If it is invalid or makes no useful progress, return actionable feedback to that agent and then pause with Continue or Redirect when the bounded recovery policy is exhausted. Never claim that missing requirements caused it without evidence. Keep full sensitive request and command content out of operational telemetry and default terminal logs; diagnostic access must follow the project's privacy controls.

## Permissions, privacy, and operational defaults

The default configured build should feel continuous after the user has reviewed the project upload scope and authorized the task's model and sandbox work. Routine actions inside that approved scope do not need a fresh modal for every request. Permission expansions, destructive or external actions, changed upload scope, new teammates with broader authority, and material spending changes require review. The backend binds authority to the task, actor, tool, project, revision, and scope; UI controls alone do not enforce it.

Sandbox work is isolated from the local host, but uploaded files and operation metadata are remote. Before upload, inspect paths and file types, exclude secrets and unneeded content, and display the manifest. Never place credentials in saved sandbox files, environment metadata, commands, model prompts, or diagnostic output. Local-only execution must be clearly labeled because local copies and processes are not security sandboxes. Check account-effective Nebius concurrency, retention, and usage limits rather than assuming published beta limits apply to every account. See [Nebius security and data handling](https://docs.tokenfactory.nebius.com/sandboxes/operate/security-and-data-handling) and [limits, retention, and usage](https://docs.tokenfactory.nebius.com/sandboxes/operate/limits-retention-and-usage).

Use a small, versioned, vendor-independent telemetry interface with injectable sinks. Capture bounded counts, durations, outcomes, retries, pause reasons as codes, and branch/checkpoint counts. Keep prompts, source, responses, command text, credentials, and absolute user paths out of operational metrics. Telemetry failure must not alter permissions or fail a task. Local trace records can hold detailed diagnostics under separate retention and privacy rules. External telemetry remains disabled by default.

## Implementation contract

This is one complete product update. The numbered workstreams are an engineering order for managing dependencies, **not** a series of partial releases that defer dynamic staffing, mixed environments, or recovery. Add requirement-derived tests as each behavior is built, run the complete checks at implementation gates, and finish with the full end-to-end acceptance matrix. Do not call the plan complete because one happy-path fixture passed.

1. **Inventory and architecture decision.** Reconcile the historical rule inventory with the actual working tree, including prompts, state parsers, fallback lineups, role counts, image selection, UI copy, and tests. Evaluate whether the existing collaboration manager can be extended safely or whether a proven orchestration runtime or component should replace part of it. Compare candidates against durable per-agent threads, multi-agent messaging, dynamic staffing, concurrency, checkpoint references, restart recovery, provider independence, Nebius integration, permission hooks, observability, maintenance, and license fit. Record the decision and tradeoffs. Reuse proven patterns and components where they truly fit; do not assume another provider's managed-agent API can be inserted into Nebius without integration work.
2. **Durable domain model and migrations.** Persist task, candidate, work item, assignment, conversation thread, question, decision, staffing request and proposal, environment requirement and selection, branch checkpoint, operation, integration, approval, and recovery records. Support an arbitrary practical number of assignments subject to account-effective concurrency and user resource policies, not one field per role. Migrate saved teams and runs without losing historical messages, files, or approvals. A legacy fixed active lineup becomes historical task data, not a silent default for new work.
3. **Planning and staffing tools.** Give Pearl tools to inspect project evidence, consult available people, record and resolve decisions, form and revise a work graph, assess candidate fit, and propose assignments. Give all teammates a structured way to request consultation or staffing. Keep the agent's reasoning and language flexible while requiring evidence references and explicit state transitions. Return invalid proposals to the proposing agent for repair; do not substitute the first available candidate. Gate final team presentation on durable unresolved-question state, user review, and approved scope, not Markdown parsing or phrase matching.
4. **Agent runtime and shared context.** Continue iterative model-tool-result loops with stable per-agent threads, inboxes, relevant shared decisions, and precise revision references. Support direct messages and questions among any approved teammates and Pearl's coordination of dependencies. Persist messages before UI acknowledgment. Bound context through referenced summaries without losing decisions or pretending that a new model inherits hidden state. Allow multiple agents in each role and additional specialists during planning or execution. Prevent circular chatter with progress and resource guards rather than a fixed exchange count.
5. **Assignment-specific environments.** Replace one run-wide Sandbox image choice with work-specific requirements, catalog capability inspection, a justified image recommendation, and optional authorized probe. Prepare the approved source snapshot in each compatible image, track source equivalence across different bases, and allow per-agent local fallback after exact user approval when no image fits. Continue unaffected agents. Validate mixed Sandbox and local artifact exchange, revision lineage, and security boundaries.
6. **Branches, integration, and review.** Publish intermediate checkpoints and tool evidence from each agent. Let peers inspect published work and update their own branches under explicit revision control. Integrate compatible changes, route conflicts and changed contracts to named owners, and let multiple testers test distinct scopes or integrated revisions. Preserve independent audit judgment. Synchronize only a reviewed integration to the local source folder after a fresh preflight against user edits. Do not label image checkpoints as Git commits.
7. **Room, Settings, and recovery experience.** Render real conversations and Markdown with a maintained safe parser, readable message spacing, visible question state, assignment and environment details, inspectable files, and accurate activity. Show genuine pending transitions without preset dialogue. Style connection and model confirmations, controls, image selection, and collapsible lists consistently. Explain failures from observed diagnostics and offer relevant Continue, Redirect, reassign, change environment, or user decision actions. Keep the composer usable during recoverable states.
8. **Remove superseded behavior and review boundaries.** Delete or isolate fixed core-lineup fallback, heading-based readiness checks, scripted handoffs, phrase cleanup, keyword intent routing, whole-file response contracts, arbitrary lifetime call limits, and tag-first image choice from the new workflow. Retain justified schema, path, permission, revision, one-use approval, idempotency, service-limit, and rolling resource checks. Review IPC, provider, Sandbox, filesystem, local execution, dependency, privacy, and telemetry boundaries. Historical records may remain readable without activating the old implementation.

For every changed behavior, write tests from the requirement, including happy path, invalid input, permission denial, failure, restart, and interaction with existing features where relevant. Reproduce observed defects in regression tests before the fix where practical. Use injected providers, clocks, storage, and execution and deterministic fixtures for routine tests. Combine unit and component tests with real SQLite, filesystem, desktop, and package checks. Run the full default suite, type/build, formatting, relevant desktop smoke, and package smoke at each implementation gate. Do not remove or weaken a failing test to make the result green; update acceptance criteria only when an intentional product change is documented. Report passed, failed, and skipped separately. A skipped live check is not a pass.

### Live demonstration and definition of done

Perform a real desktop walkthrough with a fresh project and a user-selected team that does not rely on the starter three. Resolve a product question, approve a reasoned assignment set with multiple people in at least one core role, run concurrent branch work, exchange a checkpoint-linked peer message, introduce a specialist in response to actual evidence, inspect each person's activity and files, integrate and independently audit, and synchronize without overwriting a local edit. A separate local-only walkthrough must use the same communication and revision model without remote upload. Record the exact observed behavior and whether each step used a real model, a deterministic fixture, or a live Sandbox. Do not present fixture dialogue as evidence of natural model behavior.

Live Nebius acceptance must confirm actual compatible image selection, project snapshot transfer, independent branches, checkpoint inspection, peer evidence exchange, operation reconciliation, and mixed-environment behavior within the account's effective limits. Record service outcomes and unknown costs accurately without exposing credentials or project contents. If billable live validation is not authorized or a service capability is unavailable, mark the corresponding criterion **unverified or blocked**, with the reason and user options. Do not call the full plan implemented. A second reviewer should inspect the permission, data boundary, and failure design before a production-readiness claim.
